# Legend

## Basic Setup

The books of the Bible are presented here in the order they exist in the regular printed version. These books are stored in numbered folders, with each chapter's file as a numbered markdown file.

## Chapter Navigation

Every chapter page has Previous/Next links (`_input/_includes/chapter-navigation.njk`), scoped to within its own book - reading stops at the book boundary rather than continuing into the next book.

- Previous/Next are computed from the book's own chapter collection (its directory-data `tags`), sorted numerically by chapter title. The book's own index page is excluded before sorting - its title (e.g. "Genesis", "1 Samuel") isn't a chapter number, and leaving it in would corrupt the order or get it mislabeled as a chapter.
- The first chapter's Previous link goes to the book index instead, labeled with the book's own title (e.g. "← Genesis") - never "← Chapter Genesis".
- The last chapter of a book has no Next link.
- A single-chapter book (Philemon, Jude, Obadiah, 2 John, 3 John) gets only the Previous-to-index link, no Next - this falls out of the same logic above with no special-casing needed.

## Topics

Topic files group verses or verse ranges by common topic. Topic files are kept in /_input/topics as YAML-formatted Markdown. The frontmatter is the only machine-read part of the file - a `title` and a `verses` list/mapping, described below. The content area below the frontmatter is reserved for human-written longform prose about the topic; no script ever reads or rewrites it.

Example (`_input/topics/answer-with-gentleness.md`):

```
---
title: Answer with Gentleness and Respect
verses:
  - key_verses: []
  - all_verses:
      - ref: 2 Timothy 2:25
        note: ''
        file: 55-timothy-2/02
        fragment: '2:25'
---

Longform prose about the topic goes here, written by hand.
```

Only `ref` (and optionally `note`) are meant to be hand-written; `file` and `fragment` are generated (see the sync script below) - write a new entry as just `- 2 Timothy 2:25` and run the script, which promotes it to the full shape.

Each `ref` is `"<Book Title> <chapter>:<verse>"`, or `"<Book Title> <chapter>:<verseStart>-<verseEnd>"` for a range (a plain hyphen or en dash both work). `<Book Title>` must match a book's `title` exactly as it appears in that book's `index.md` (e.g. "2 Timothy", "Song of Songs").

`verses` supports three shapes, picked per topic file as needed:

- A flat list, ungrouped: `verses: [ "2 Timothy 2:25", ... ]`.
- A mapping of group name to a list: `verses: { "Key Verses": [...], "All Verses": [...] }`.
- An array of single-key group-wrapper objects, one group per array item - what both current topic files use (see the example above, and `_input/topics/church-discipline.md`): `verses: [ { key_verses: [...] }, { all_verses: [...] } ]`. This form keeps an explicit, unambiguous group order (a plain mapping's key order is conventional, not YAML-spec-guaranteed) and reads naturally as `- key_verses:` / `- all_verses:` in the file.

Grouping is purely organizational, regardless of shape - every reference in every group is resolved, validated, and cross-linked exactly the same as a flat list's; the topic page renders each non-empty group under its own heading (literally the group's key, e.g. "key_verses" - not auto-formatted into "Key Verses") instead of one combined list. An empty group (`key_verses: []`) is valid - a placeholder for later - and is simply skipped when rendering.

`note` is a short annotation for why that verse belongs to the topic. It's always present (empty string when unused) so every entry shares one consistent shape. It's resolved alongside its reference and shown next to the link on the topic page - but it is not copied into the referenced chapter's `topics:` frontmatter, which stays identical either way.

At build time, `lib/verseRefs.js` resolves each `ref` to the matching chapter page and verse anchor automatically - book folder names and chapter-filename zero-padding (which varies by book, e.g. Genesis uses `01.md` but Psalms uses `001.md`) are never written by hand, and the live site never reads `file`/`fragment` back as authoritative - it always re-resolves `ref` itself. For example, "2 Timothy 2:25" resolves to the chapter page for 2 Timothy 2 (`/books/55-timothy-2/02/`) with the verse anchor `#2:25`.

Topic pages are published under `/topics/<topic-filename>/`, listed at `/topics/` (linked from the home page). Every chapter that a topic touches shows a "Topics in this chapter" block (`_input/_includes/chapter-topics.njk`) listing that topic and any other chapters sharing it - this cross-linking is computed at build time by the `chapterTopics` collection in `.eleventy.js`, from the `verses` lists across all topic files; it is never hand-maintained on the chapter side.

After adding or editing a topic file's `verses` list, run `npm run topics:sync-links` once ([scripts/sync-topic-source-links.js](../scripts/sync-topic-source-links.js)). It only ever touches frontmatter - never a topic file's content area - computed from `verses`, never hand-written on either side:

- In the topic file's own `verses` frontmatter, it enriches every entry in place with `file` (the chapter's path, relative to `_input/books/`, with no `.md` extension) and `fragment` (chapter:verse anchor), promoting a bare string to the full object shape if needed. Edit `ref`/`note` and re-run the script rather than touching `file`/`fragment` directly - they're overwritten from scratch on every run, and whichever of the three `verses:` shapes above you used is preserved, not silently converted to a different one.
- In each referenced chapter file's frontmatter, it writes a `topics:` list naming every topic verse that touches that chapter, one entry per `"<topic-slug> <chapter>:<verse>"` (e.g. `topics:\n  - answer-with-gentleness 2:25`) - using the chapter's own anchor format, so a chapter with several verses tied to the same topic (like 1 Peter 3's `3:8` and `3:15-16`) gets one entry per verse rather than one ambiguous slug. Entries are removed once their topic/verse is no longer referenced. Metadata only - it never touches a chapter's scripture text, and isn't rendered on the site either (the "Topics in this chapter" block there is computed independently, at build time, as described above). It exists purely so the association is visible when reading a chapter file's own frontmatter directly.

Re-running the script at any time is always safe - it produces no diff when nothing has changed.
